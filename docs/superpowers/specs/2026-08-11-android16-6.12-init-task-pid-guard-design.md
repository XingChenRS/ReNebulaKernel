# Android 16 / 6.12 `init_task` PID Guard Design

## Objective

Stop both PID-related panic paths captured on the Vivo PD2502 while preserving
the upstream `SET_INIT_PGRP` behavior. The verification build remains the
locked Android 16 / 6.12.92 snapshot with ReSukiSU and SUSFS enabled, KPM and
Vivo vermagic disabled.

## Evidence

The unadapted 6.12.92 image panics in `change_pid()` after
`do_set_init_pgrp()` passes `ffffffdf00000000` as the new process-group
`struct pid *`. The PID1 adapter delays the failure, but the later image still
panics in `__task_pid_nr_ns()` while `CpuTracker` reads PID0 statistics; that
trace loads `ffffffd100000000` from `init_task.signal->pids[PIDTYPE_PGID]`.

The exact built Image has these link-time offsets from the arm64 image base:

- `init_task`: `0x268da00`
- `init_struct_pid`: `0x26a32f8`

With the later trace's KASLR base `ffffffd138000000`, the expected live
addresses are therefore `ffffffd13a68da00` and `ffffffd13a6a32f8`. The trace
contains the former as the task argument but contains `ffffffd100000000` as
the loaded PID pointer. The pointer retained only its upper 32 bits.

Google's locked 6.12 source initializes every PID slot of `init_signals` to
`&init_struct_pid`. PID0's process-group and session identity are therefore
known invariants; PID1 is not the intended substitute. KernelSU's upstream
feature intentionally joins the immortal PID0 process group and falls back in
userspace only when the ioctl returns an error.

## Root-provider repair

Replace the repository's `pid1-init-pgrp-v1` compatibility adapter with
`pid0-canonical-pid-v2` for all three root providers and both linkage
artifacts.

The adapted `do_set_init_pgrp()` must:

- keep the upstream lock, permission check, version-dependent `change_pid()`
  call, and `free_pids()` behavior;
- use `&init_struct_pid` directly in built-in builds;
- use `task_pid(&init_task)` under `MODULE`, because `init_task` is exported
  while `init_struct_pid` is not, yielding the same PID0 object without
  reading the corrupted signal PID slots;
- use that canonical object for both the PID0 session comparison and the new
  process group;
- never look up PID1 and never dereference `task_pgrp(&init_task)` or
  `task_session(&init_task)`;
- preserve exact-anchor drift rejection and record the adapter ID in
  `renebula-root-record.json`.

This preserves the stealth property that motivated `SET_INIT_PGRP`; it does
not reduce the operation to `setpgid(0, 0)` and does not disable the ioctl.

## Android 16 / 6.12 core guard

Add a separate, auditable kernel compatibility adapter. It applies only to
Image-producing variants whose family is exactly `android16-6.12`. It does not
apply to LKM artifacts or any other KMI family.

In `common/kernel/pid.c`, introduce one RCU-only read helper around
`task_pid_ptr()`. For ordinary tasks it returns the existing pointer unchanged.
For `task == &init_task`, if a PID slot no longer equals `&init_struct_pid`, it
logs one rate-independent warning and returns `&init_struct_pid` without
dereferencing the corrupted value. Both `get_task_pid()` and
`__task_pid_nr_ns()` must consume this helper.

The guard is deliberately read-only: it does not rewrite PID lists, detach
tasks, or attempt to infer whether an arbitrary kernel address is valid. The
adapter must match the locked 6.12 source anchors exactly, refuse partial
writes on drift, and write `renebula-compat-record.json` even when the current
variant is out of scope.

## Workflow and provenance

The single workflow invokes the compatibility adapter after root-provider
materialization and before feature patches or compilation. Successful and
failed artifacts include `renebula-compat-record.json` so a boot image can be
traced to this mitigation.

No public workflow option is added. This is a source-family compatibility
policy derived from a confirmed invariant, not a user-selectable Root, SUSFS,
KPM, vermagic, or uname feature.

## Verification

Repository tests must prove:

- all providers/linkages use the linkage-safe canonical PID0 object and contain
  no PID1 lookup or `init_task.signal->pids[]` read;
- the 6.12 Image adapter patches exactly the two risky readers and records its
  ID;
- LKM and non-6.12 variants remain byte-for-byte unchanged apart from their
  explicit no-op record;
- source-anchor drift aborts before writing;
- workflow ordering and artifact provenance include the new adapter.

After local tests and repository validation pass, push the commits and run the
single workflow with:

- release: `android16-6.12-lts-2026-08-03`
- root source: `resukisu`
- SUSFS: `true`
- KPM: `false`
- Vivo vermagic: `false`
- uname tag: empty

The CI result proves build integration only. Boot success remains a device-side
test, and any surviving panic must be assessed independently rather than
attributed to this guard without a new trace.
